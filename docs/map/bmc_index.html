BMC / OpenBMC 文章索引

本頁整理知識庫中所有 BMC / OpenBMC 筆記，依主題分類，方便從「想做什麼」找到對應文章。 名詞定義請參考 BMC 名詞表。

一、OpenBMC 架構與建置​

文章內容
OpenBMC 總覽全貌：Yocto 建置（recipe .bb／.bbappend／meta-layer、build 產物與工作目錄路徑、唯讀 rofs + rwfs overlay），核心元件（phosphor-dbus-interfaces、entity-manager、phosphor-logging 與事件子系統），對外介面（Redfish、bmcweb 的 D-Bus→JSON 翻譯角色、SSE 長連線收事件）
D-BusOpenBMC 的通訊骨幹：service／object path／interface／member 四層定址，property·method·signal 三種成員；busctl list／tree／introspect／get-property／call／monitor 逐一示範，含 type signature 對照表；末段講如何用 YAML + sdbusplus 建立自己的 service
Entity Manager用 JSON（Exposes／Probe）描述板上硬體並開機時動態探測，命中後把設定放上 D-Bus 供 dbus-sensors／pid-control 訂閱；一份 image 支援多板型，新增硬體多半只加 JSON 不改 C++
Yocto ProjectOpenBMC 的 firmware image 建置框架：bitbake／recipe(.bb)／.bbappend／layer(meta-*)，. setup <machine> 後 bitbake obmc-phosphor-image，產物落在 tmp/deploy/images/
在自己的筆電上開機 NVIDIA GB200 NVL 的 BMC firmware把上面那套 Yocto 流程實際跑一遍的完整紀錄，對象是 OpenBMC 樹內 meta-nvidia 的 gb200nvl-obmc——真實資料中心平台的 BMC 設定，且 QEMU 自 10.1 起內建由 NVIDIA 送上游的 gb200nvl-bmc machine，不需要實體機櫃。先讀 machine conf 能得到什麼（flash 分割 64 MB、require pldm.inc 讓 PLDM／MCTP 是平台原生而非自己加、QB_MACHINE 直接寫好怎麼開）。三個坑：發行版的 QEMU 太舊而 bitbake qemu-system-native 可以免 sudo 生一份 11.0.2（該 recipe 沒有任何 machine patch，反過來證明 machine 已在 upstream）；編出來的 QEMU 要設 LD_LIBRARY_PATH，否則載到系統舊版 libslirp 而報 SLIRP_4.9 not found；30 GB RAM 配 -j 16 會被 OOM killer 砍掉 cc1plus，要降平行度並開 BB_PRESSURE_MAX_MEMORY。最後用 PLDM 交握驗證——pldmd 自己就是 responder，不需要 host，在 lo 上指派 EID 後 pldmtool base GetPLDMTypes，並把 raw 位元組對回 DSP0240 header 自行驗算。末節誠實劃線：這證明的是軟體側能力，不是硬體 bring-up 經驗
Git / Gerrit WorkflowOpenBMC 上游的 Gerrit code review 流程：一個 commit = 一個 change，用 git review 推送、Change-Id 追蹤修訂、Code-Review +2 才可合併、每個 commit 要 Signed-off-by

二、管理介面（IPMI / Redfish / SSE / SOL）​

文章內容
IPMI頻外管理標準：KCS／RMCP+／IPMB 傳輸介面；SEL（非揮發事件日誌）、SDR（感測器描述與換算門檻，非讀值）、FRU（零件身分資料）三者的分工；ipmitool raw 的 NetFn／Cmd 格式與 OEM command 用法；末段講與 Redfish 的世代關係
IPMI 驗證實戰（一）：基礎觀念與通用測試方法驗證系列的入口：為什麼「回 00」不代表功能正確；NetFn 對照、in-band／out-of-band、常見 Completion Code（C5／CC／D4…）與出現情境；一套可套用到所有命令的方法：raw 與 string 雙驗證、Set→Get→還原、負面測試、cold reset／AC cycle 後的持久性、用實機行為與 SEL 判定
IPMI 驗證實戰（二）：各命令類別的測試重點依 NetFn 逐類整理命令、ipmitool 用法與測試重點：App（Device ID、Watchdog 的 byte 定義與觸發驗證、Session／Cipher Suite 安全檢查、User 權限）、Chassis（電源控制、Power Restore Policy 拔插 AC、Restart Cause、Boot Options）、Sensor／Event（人為觸發 UNC event）、Storage（FRU 先備份、SDR、SEL 的 Reservation ID 與 Clear 流程）、Transport（LAN、SOL baud rate）、DCMI
IPMI 驗證實戰（三）：OEM 命令、韌體更新與命令速查OEM 命令（NetFn 0x2E 帶 IANA、0x30–0x3F）的測試原則；韌體更新的測試矩陣（升降版 × in-band／out-of-band × 主機狀態 × 對象 × 異常情境）與燒錄後檢查項；整個系列的 ipmitool 速查與結語
RedfishDMTF 的 RESTful 管理介面（HTTPS + JSON），資源導向、標準動詞，目標取代 IPMI；OpenBMC 由 bmcweb 把 D-Bus 資料對映成 /redfish/v1/ 底下的 Systems／Chassis／Managers 等資源
Redfish EventServiceRedfish 事件訂閱機制：POST 到 EventService/Subscriptions 帶 Destination 與過濾條件，事件發生時 BMC 主動推送，免管理端輪詢；遞送方式分 push(webhook) 與 SSE
Server-Sent Events (SSE)基於 HTTP 的單向串流（text/event-stream），client 開一條長連線即時收事件，免預先註冊 webhook destination；比 WebSocket 簡單但只能單向
SOL（Serial over LAN）概念與運作要點：BMC 把 host serial 封進 IPMI over LAN（RMCP+、UDP 623）轉給遠端 client，ipmitool -I lanplus ... sol activate 啟用，跳脫序列 ~.
Serial over LAN（完整版）SOL 的詳版筆記：元件角色表、封包走向圖、RMCP+ 封包格式、ipmitool 指令表與使用場景，並提到 Redfish ConsoleService（WebSocket 串流）取代 IPMI SOL

三、硬體存取與匯流排​

文章內容
BMC 硬體入門總覽這一節的入口：從電子電路一路串到管理協定的地圖。歐姆定律／被動 vs 主動元件表／open-drain 與上拉電阻為何是 I2C 的前提／分壓比與 ADC 換算；I2C 交易時序圖與 --／數字／UU 三態、SMBus 與 PMBus 的三層堆疊對照；SPI 靠 CS 選裝置；UART（Controller vs COM Port 的分工、8N1 frame 組成、/dev/ttyS0 對照表、device tree 裡的 UART routing）；EEPROM 位址寬度／page size／WP# 三個坑、TMP75 的 0.0625°C/LSB 與 word 模式 byte order 實例（0x1027 → 39°C）；MCTP／PLDM／SPDM 分層圖；AST2600 規格表；末段六題可上板操作的練習
Hardware（硬體存取）週邊介面總覽：I2C 協定要點與 i2cdetect／i2cget／i2cset／i2ctransfer／sysfs 動態綁定；I2C→SMBus→PMBus 三層堆疊差異表；EEPROM 與 FRU 的容器／內容關係；SCM 與 OCP DC-SCM／DC-SCI；GPIO 新舊介面對照（libgpiod vs 已 deprecated 的 sysfs）；devmem、ADC（IIO + 分壓比）、SPI 的 single／dual／quad／octal 模式
PMBus電源管理協定：P=IV 拿來驗證換算與算轉換效率；Linear11／Linear16／Direct 三種資料格式的公式與適用暫存器（移植最常見的 bug 來源）；Read/Write × Byte/Word 交易型態對照 kernel API 與 page 分頁機制；常用 command code 表；probe() 流程與 i2cdetect 的 --／數字／UU 三態判讀
Device Driver（統整）Driver 與 Device Tree 關係圖、SMBus／PMBus 筆記、Linear11 浮點格式，以及 user space → PMBus core → driver read_word_data → I2C 的呼叫鏈；另有 Kconfig／Makefile／binding yaml 的檔案位置對照
Porting PMBus Driver完整實作指南：讀 schematic 找 bus → 寫 device tree node（compatible／reg）→ Kconfig／defconfig／Makefile → 填 pmbus_driver_info 與 .read_word_data → binding yaml → 用 dd 拼 image 上板燒錄 → 用 P=I*V 驗證
Device Tree為何 ARM 需要 device tree（週邊不可列舉）；dts／dtsi／dtc／dtb／dtbo 工具鏈與反編譯；compatible 作為硬體↔driver 的配對鍵（probe 沒被呼叫的頭號原因）；phandle 與 #*-cells 的引用機制；/delete-node/／/delete-property/；binding YAML 與 make dtbs_check；開機時 dtb 的傳遞路徑與 devtool modify 修改流程
CPLD板上可程式邏輯裝置（非揮發，開機即運作）：伺服器用它做 power sequencing、reset／clock 邏輯、glue logic、presence／strap 讀取；BMC 經 GPIO／I2C／JTAG 與它互動，並可在板做 in-system programming
PCIe Retimerretimer 用 CDR 重新取樣、重建 PCIe 訊號以延長走線（對比 redriver 只放大不重生時脈）；BMC 經 I2C／SMBus 讀 eye margin，並用 I2C 或 PLDM(Type 5) 更新其韌體
FRU（Field Replaceable Unit）FRU EEPROM（IPMI FRU 格式）存製造商／序號等資產資訊，掛在 I2C bus；有 at24 driver 時 hexdump -C eeprom，無 driver 時用 i2ctransfer 直讀，ipmitool fru 解析成人類可讀欄位
GPIO Hog在 device tree 用 gpio-hog 宣告某支 GPIO 開機時即被 kernel 佔用並設固定狀態（enable／reset／power-good），早於大部分服務啟動，但被 hog 的 pin 之後不能再被別的 driver 或 user space 請求
Linux 中斷處理（Interrupt）IRQ 機制與 /proc/interrupts 觀察；top half（interrupt context、不可睡眠、只做 ack 與記錄）／bottom half（softirq／tasklet／workqueue，其中 workqueue 可睡眠）；request_irq() 註冊 handler 回傳 IRQ_HANDLED／IRQ_NONE
I2C Hotplugi2c-hotplug：在可熱插拔裝置（模組／cable card／riser）出現或消失時，由 presence GPIO／interrupt 觸發，動態建立或移除 I2C bus 與 device node，重點是拔除時要乾淨移除避免殘留 stale 節點
MCTPDMTF PMCI 家族的傳輸協定，用 EID 定址、與底層匯流排無關，可跑在 SMBus／I2C、PCIe VDM、USB、Serial、KCS；上層承載 PLDM、NC-SI、SPDM，OpenBMC 以 libmctp／mctpd／pldmd 實作
Schematic 判讀從電路圖推出 device tree：畫出 I2C topology、電路圖 bus 編號 ≠ Linux /dev/i2c-N（mux channel 會另外編號）；address table 與 7-bit vs 8-bit 位址的經典混淆；timing 面的上拉電阻、速度取全 bus 最低、電壓域 level shifter、上電順序；最後給 mux 前後兩種 dts 寫法
Spec / Datasheet 判讀讀 datasheet 的固定順序（block diagram → pin → 位址 → register map → 資料格式 → timing）；以 TMP75 為例算出 0.0625°C／LSB 的換算；EEPROM datasheet 的位址寬度／page size／write cycle／WP 腳重點；i2cget 手動驗證與 word 模式 byte order 的坑；末附 datasheet 章節↔程式碼的對應表

六、開機流程​

文章內容
BMC 開機流程精簡版三階段（bootloader／u-boot → kernel zImage → rootfs／systemd）說明，附 flash 多 image slot（A/B fail-safe）與 uImage／FIT image 補充
OpenBMC Boot Flow最完整的一篇：從 SoC 上電、Boot ROM、U-Boot SPL／Proper、kernel、OverlayFS rootfs、systemd target 到核心服務與 Host 電源管理，含 flash layout、kernel cmdline、除錯指令與常見開機失敗原因表
Flash 燒錄MTD 子系統與 flash 的擦除/寫入限制；/dev/mtdN（char）vs /dev/mtdblockN（block）該用哪個；flashcp／flash_erase／nandwrite／dd 的差異與 為什麼不能用 dd 寫 flash（只能 1→0，會得到 bitwise AND 的壞 image）；更新 BMC 的 Redfish／tarball 標準流程 vs 直寫 MTD；A/B slot fail-safe 與更新 u-boot 的變磚風險
systemdunit 型別與 .service 關鍵欄位（Type=dbus 在 OpenBMC 的用途）；target 是同步點不是程式，對應 OpenBMC 的電源狀態機 target；unit 檔三層路徑優先序、enable 的 symlink 實作、drop-in 覆寫；journald 是二進位格式必須用 journalctl，以及 BMC 上 journal 預設只在記憶體、重開就消失的坑

九、資料中心與叢集​

文章內容
LinuxBoot 與 u-root韌體側的鄰居：把 UEFI 的 DXE 之後換成放在 SPI flash 裡的 Linux + u-root initramfs，再用 kexec 跳進正式 OS。與 BMC 的分工是——BMC 管上電、power cycle 與更新 host SPI flash，LinuxBoot 管 host 自己開機那一段。概論版見 LinuxBoot
資料中心叢集架構cluster 節點角色分工（headnode／compute node／storage node、job scheduler 如 Slurm/PBS）與 BMC 的關係：每個節點內建 BMC，經 out-of-band 管理網路（IPMI／Redfish）遠端開關機、監控、更新韌體
Telemetry、OpenTelemetry、BMC 與 Grafana/Loki 的關係把 BMC 放進整套 observability 架構裡看：telemetry 的四類訊號、OpenTelemetry 管的是產生與傳輸（SDK／OTLP／Collector）而不管儲存、BMC 作為 out-of-band 來源（OpenBMC 內 dbus-sensors → telemetry daemon → bmcweb 的資料流、Redfish TelemetryService 的四種資源、pull 與 push 兩種取法）、LGTM stack 的分工與 Loki 只索引 label 的取捨；最後用「風扇故障 → 降頻 → 服務變慢」示範跨層找根因。實作層面的 PoC 見 Shell Collector / VictoriaMetrics / Grafana

十、開發板除錯與自動化工具​

文章內容
pyftdi / FT2232H / PCA9555用 PC 直接當 SPI／I²C／GPIO master：FT2232H 的雙通道與 MPSSE 引擎、pyftdi 的 I²C／SPI／GPIO API 範例；PCA9555 暫存器表（Input／Output／Polarity／Config）、位址 0x20–0x27、INT# 腳；組起來做 board farm 治具撥 reset／power enable／boot strap。踩雷：ftdi_sio 搶裝置、I²C 要外接上拉、MPSSE I²C 對 clock stretching 支援差、1.8V 域要 level shifter、URL channel 是 1-based
com0com / com2tcpWindows 虛擬 null-modem 對（CNCA0 ↔ CNCB0）與 COM↔TCP 橋接；hub4com 一對多分流與 RFC2217；setupc.exe 管理與 EmuBR／EmuOverrun 兩個關鍵參數；Linux 對應端 ser2net／socat／tty0tty；典型組合是把機房板子的 UART 拉到桌機 PuTTY；坑：驅動簽章、baud 設定在虛擬對上不生效、斷線不自動重連
MediaMTX / RTSP / ONVIF先分層：ONVIF 控制面（WS-Discovery、GetStreamUri、PTZ）、RTSP 訊令面、RTP/RTCP 資料面、MediaMTX 轉發；MediaMTX 代理真相機、sourceOnDemand、錄影保留、用 FFmpeg loop 影片檔當 CI 假相機；Python 自動探索 ONVIF 相機並產生 MediaMTX 設定；常見坑表（ONVIF 401 是時間差、多播跨不了 Docker bridge、UDP 丟包破圖）
Shell Collector / VictoriaMetrics / Grafana採集 → 儲存 → 視覺化的指標管線：node_exporter textfile collector 與 exec input 讓 script 變成資料來源、VictoriaMetrics 當 Prometheus 相容 TSDB、Grafana 畫趨勢與 annotation；半天可跑的 PoC（CI job 直接 curl push）；注意 label cardinality、atomic write、gauge vs counter
設備租約與遠端除錯通道設計筆記：把開發板的除錯介面遠端化並加上互斥。核心是 capability（一平台一 driver）× transport class（只有 byte-stream／usb-device／tcp-service／rpc 四種） 兩層拆分；中央服務不在資料路徑上；composite lease 原子發放防死鎖、TTL 由 agent 自主倒數、epoch 防重放；Android（adb proxy 過濾 host:devices）、OpenBMC（BMC 開發必須租 bmc:uart0+bmc:flash+:power 才有救援路徑）、RISC-V（ConflictsWith() 宣告 jtag 與 power 衝突）三個平台驗證抽象；附失效模式表與實作順序

建議閱讀順序​

想看懂 OpenBMC 怎麼從上電跑到服務就緒：

BMC 開機流程（bootup）
   → OpenBMC Boot Flow          ← 主線：上電 → U-Boot → kernel → rootfs → 服務
   → systemd                    ← init 系統與 target 啟動順序
   → Yocto Project              ← 這些服務是怎麼被 build 進 image 的
   → Redfish / IPMI             ← 開機後對外的管理介面

想在 OpenBMC 上加一顆新的 sensor：

Schematic 判讀（i2c topology / address table）
   → Device Tree                ← 把新裝置寫進 dts
   → Porting PMBus Driver       ← 主線：driver 落地與驗證
   → hwmon                      ← 讀值怎麼出現在 /sys/class/hwmon
   → Sensor Porting             ← hwmon → dbus-sensors → entity manager → fru
   → Entity Manager             ← 用 JSON 描述硬體、動態探測
   → PID Control / Thermal      ← 讓風扇跟著這顆 sensor 轉

待補主題​

用第一性原理拆 BMC：它的本質是「獨立於主機、監控與控制伺服器的管理處理器」，心智地圖是 監控 → 控制 → 遠端介面 → 通訊協定 → OpenBMC 軟體棧 → 韌體更新 → 安全 → RAS。目前筆記在 監控（sensor／thermal／power）、OpenBMC 軟體棧、管理介面 很紮實，但往「協定現代化、更新、安全、RAS」這幾條軸線走就出現缺口。下表依重要性排序。

主題為什麼重要狀態
韌體更新流程（Redfish UpdateService／code update／A/B image）Flash 燒錄 已補上 MTD 層的燒錄工具比較、Redfish UpdateService 與 tarball 兩種標準更新路徑、A/B slot fail-safe 的概念。仍缺的是更新服務的內部機制：phosphor-software-manager 的狀態機、image 簽章驗證流程、寫入備援 slot 後如何切換、開機失敗自動回滾的實作部分補齊
PLDM（Platform Level Data Model）MCTP 這篇把 PLDM 當成「MCTP 上承載的訊息類型」一句帶過，但 PLDM 本身的酬載——監控（Type 2）、FRU（Type 4）、firmware update（Type 5）——沒有專篇。這是逐步取代 IPMI 的現代 DMTF 協定，pldmd 已在 boot flow 出現卻無文章待補
BMC 安全（Secure Boot for BMC／SPDM attestation／Redfish 角色權限／host-BMC 隔離）全知識庫沒有一篇談 BMC 側的安全；MCTP 僅把 SPDM 當訊息類型提一下。BMC 是伺服器最高權限的旁路處理器，一旦被攻陷等於拿下整台機器，Secure Boot、attestation、Redfish AccountService 權限模型都是空白待補
KVM / 虛擬媒體（iKVM、virtual media）SOL 與 Serial over LAN 只涵蓋文字序列埠 console。遠端圖形畫面重導與掛載虛擬光碟／USB（裝 OS、進 BIOS 設定）是遠端管理的另一半，目前完全沒有待補
RAS / crashdump（記憶體錯誤記錄、host 當機資訊收集）Event Log 與 sel-logger 記的是 BMC 自己的事件，但 host CPU/記憶體的 MCA/MCE、host crashdump（透過 PECI／PLDM 收集）這類 RAS 機制沒有。資料中心靠這個判斷該不該換機器待補
KCS / BT / SSIF（BIOS ↔ BMC 的 in-band host interface）KCS 只在 OpenBMC Boot Flow 與 MCTP 當成 IPMI 傳輸介面之一被提到。host 端 BIOS/OS 怎麼透過 KCS／BT／SSIF 與 BMC 溝通（送 SEL、要 boot option、post 狀態）這條 in-band 通道沒有專篇待補
NC-SI（BMC 與主機共用網卡的 sideband）Network 只講 phosphor-networkd 管 IP／DNS／VLAN；MCTP 提了「NC-SI over MCTP」一詞。但 NC-SI 本身——BMC 如何透過 sideband 共用 host 的 NIC 做管理流量、與專用管理埠的取捨——沒有文章待補
POST code / 主機開機除錯（port 80 BIOS POST code 透過 BMC 讀）host 卡在開機時，BMC 讀 port 80／LPC/eSPI 上的 BIOS POST code 是第一線除錯手段。SOL 能看 console 輸出，但 console 還沒起來時就得靠 POST code，目前無筆記待補
